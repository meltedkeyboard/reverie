# Codebase map

Where things live and how they connect. For setup and features see the [README](README.md).

Stack: Expo 57, React Native 0.86, expo-router, expo-sqlite, TypeScript (strict). iOS and Android. Path alias `@/*` points to `src/`.

## Search

A Spotlight-like search over everything, in `(tabs)/search/index.tsx`.

- Characters, rooms (by name or a member's name) and chat titles (a scene's with its cast, `cast` of `SearchChat`) are loaded whole on focus and matched in JS, where case folding works for Cyrillic. `listSearchChats` also serves the "Recent" list shown for an empty query.
- Message text is matched in SQL by `searchMessages` (`src/db/search.ts`), from two characters on, debounced. SQLite folds case only for ASCII, so the query is tried in four spellings (as typed, lower, capitalized, upper).
- Settings results are a static list of entries with keywords, each pointing at `/settings?section=…` (`SettingsSection` in `src/lib/core/searchScope.ts`).
- The order of sections follows the tab search was opened from: the tabs layout reports each focus to `noteTabFocus`, and search reads `getSearchScope` (`ORDER` in the screen).
- Header styling: transparent header with top `EdgeFade` (`styles.fade`) and native `EdgeFade` scroll bleed-through. On iOS, `<TabTitle>` is positioned on the left via `unstable_headerLeftItems` / `headerLeft` with `hidesSharedBackground: true` to avoid the capsule background and keep the center clean (`title: ''`). In landscape (`width > height`), the native search bar integrates inline into the navigation bar (`placement: 'inline'`), leaving the vertical viewport clear for results. Rows react to press with a native iOS opacity feedback (`styles.rowPressed`).
- A message result opens `/chat/ID?message=ID`; `ChatThread` scrolls to the row and tints it with `Flash`. Settings blocks use the same `Flash`.

Some data cannot go through route params (file URIs, callbacks, very long data URLs), so tiny module-level slots carry it between screens: `src/lib/images/backgroundDraft.ts`, `src/lib/images/avatarCrop.ts`, `src/lib/chat/textDraft.ts`, `src/lib/chat/genDraft.ts` and `src/lib/images/viewer.ts`.

Originals and framing: a still avatar or chat background is stored twice, like a photo and its edit in the Photos app. The original goes in untouched (`persistOriginal`, in the same `avatars` / `backgrounds` folder under its own name), and the framed copy that every screen shows stays the plain `avatar` / `background` file (a 512 px square JPEG, a 1600 px JPEG), so nothing that displays pictures had to change. The frame is a JSON `{originX, originY, width, height}` in pixels of the original (`CropRect`, `cropToJson` / `cropFromJson`), kept in `avatar_crop` / `background_crop`; an avatar's frame also keeps the original's size (`sourceWidth`, `sourceHeight`, set by `/avatar-crop`), which the viewer needs to open the original out of the avatar, and for a frame made before that it measures the original once (`pictureSize` in `avatars.ts`); the originals in `avatar_original` / `background_original` (characters) and `background_original` / `background_crop` (rooms). "Adjust framing" in the editors reopens `/avatar-crop` or `/background` on the original with the old frame (`crop` in the draft) and gets a new copy and frame back. Pictures saved before originals existed have none: reframing then takes the framed copy itself and keeps it as the original. A moving avatar is its own original and cannot be reframed. Originals ride along in the backup (their own files in the zip) and in folder sync (`referencedImages`), and `removeCharacterImages` / duplicate handle them.

Avatars may move: a GIF, animated WebP/APNG (expo-image plays them) or MP4/MOV/M4V (expo-video). A moving file skips the crop and is stored untouched under its own extension (`persistAvatar`, `copyStoredImage` and backup import keep it); `contentFit="cover"` shows its middle. Over the avatar limit (15 MB by default, set or switched off in Settings > Size limits) it is refused.

Chat backgrounds and the global wallpaper may move too, in the same formats. `pickBackground` takes them from the library or Files (the camera gives a still shot) and refuses WebM and a file over the background limit (30 MB by default). Nothing can cut a frame out of a GIF or a video, so a moving background is its own original: `/background` frames it as it does a still one, but hands back the file itself with the frame, and the frame (`background_crop`, `chat_wallpaper_crop`) also keeps the size of the file (`sourceWidth`, `sourceHeight` of `CropRect`); `background_original` stays empty. `ChatBackground` tells a moving file by its header (`movingKind`) and draws it whole through `Picture`, laid out so the frame covers the view (`placeCrop` in `backgroundFrame.ts`, which centers the frame and never leaves a gap). Its blur is a `BlurView` over it (a `BlurTargetView` around the picture for Android, `backdrop-filter` on the web), as expo-image's `blurRadius` is worked out once over a single frame on iOS and a video has none; still pictures keep `blurRadius`. A moving background moves wherever it is shown, the thumbnails in the editors, the profile, the custom tile of Appearance and the blurred backdrops included, and holds its first frame only under Reduce Motion; a video also pauses while its screen is not focused (a picture stops by itself once a pushed screen takes it out of the window). `Picture` takes `paused`: a paused video plays until its time moves and stops there, as a player never started shows nothing and iOS cannot take a frame of some files as a picture (`generateThumbnailsAsync` fails with "Cannot Open"), and a playing one starts again as the app comes back. In the editors `useImageSlot` keeps a moving pick without an original (`setFramed`), reframes it from itself at its frame (`adjustSource`, `shownCrop`) and does not copy a stored one again when only its frame changed (`persist`).

Every avatar opens the viewer: `Avatar` and `AvatarStack` (the whole cast, via `castGallery`) wrap themselves in `ImageLink` unless `viewable={false}`. They hand over the avatar's file too (`avatar` of `ViewerImage`, also from `ExpandingAvatar`), by which the viewer finds the original it was cut from; a fresh pick in an editor has none until it is saved. `ImageLink` measures itself as it is tapped and hands the viewer the place and the `corners` of the picture (one radius, or each corner's: a character card cuts the avatar filling its edge only on that side, `CARD_RADIUS` of `ListCard`), so it grows out of it and lands back in it; `AvatarStack` gives the place of each face (`spots`), `ExpandingAvatar` works out its own from its block, and a single picture hides while it is up (`setLifted` in `src/lib/images/viewer.ts`, `useLifted`). In a list row that opens something, the avatar keeps its own tap (the rest of the row still opens). `viewable={false}` is for places where the tap on the avatar itself must do something else: a header menu trigger, the cast button, a cast sheet row, the Continue capsule, the character picker in the room editor. Where it matters, the photo is offered as a menu item through `useOpenViewer` instead.

## Data flow of a chat

1. `chat/[id].tsx` loads the chat and character, then mounts `useChat`.
2. `useChat` builds the request: system prompt from the character, the active user persona (`chat.persona_id` or the default persona from `personas`, formatted via `formatPersonaPrompt` in `src/lib/chat/persona.ts`), the newest messages that fit the context window set in Settings (`fitHistory`, minus the system prompt and `tokenLimit`: the character's `maxTokens` for the reply plus its `reasoningBudget` unless thinking is off, which is also what goes out as `max_tokens`; LM Studio is also sent `thinking_budget_tokens`, with which it cuts the thought off and lets the model answer) using the selected variants, images as `image_url` parts.
3. `streamChat` (`src/api/llm.ts`) yields `StreamPart`s: reply text and reasoning. `useChat` updates state per chunk and writes to the DB through `src/db/messages.ts`.
4. `regenerateTargetAt` decides what a regenerate replaces and which history the model sees.
5. After the first reply `autoName` calls `suggestTitle` and stores the title with `setChatTitle`. The title is asked for with thinking off, regardless of the character; if the model still answers with nothing, it is asked again with the server default and a larger budget.
6. Multiple assistant replies are kept as variants (`message.variants`). With more than one, the message's menu has Delete version (`deleteVariant` action, `removeVariant` of `useConversation`, `deleteVariant` / `withoutVariant` in `src/db/messages.ts`: the one shown goes with its thought and refine, the one before it is shown) beside Delete message. Stepping through them with `Pager` in `MessageRow.tsx` dynamically keys `Markdown` (`key={message.streaming ? 'stream' : `${message.variant}:${message.content}`}`) and `ThoughtBlock` (the same with a `thought` prefix, since the two are siblings and a shared key clashes); which thoughts the reader unfolded is kept outside the rows (`unfolded` in `MessageRow.tsx`, by message and version, or by chat for the reply being written, which the saved reply with the same thought takes over), since a recycled cell loses its state, and the thought's header is a UI-thread `Gesture.Tap`, which a scroll of the list following the reply does not cancel as it did a Pressable; a tap on the thought's lines folds and unfolds it too, while a longer press selects the text and a tap that clears a selection is ignored (`SelectableText`'s `onSelect`); while the model still thinks, and on the text of a reply being written, a finger holds the text as it was (`useHeldText` in `MessageRow.tsx`, told of the selection through `onSelect` of `SelectableText` and `Markdown`) until it lets go with nothing selected or the selection is cleared, since the text replaced each frame dropped the selection, and `MarkdownView` keys each `Block` by text (`key={streaming ? views.length : `${views.length}:${text}`}`), forcing Yoga to remount and recalculate the intrinsic height of the selectable `TextInput` without clipping or leaving blank space at the bottom.
7. Refine ("Refine..." in a message's menu) regenerates with a wish of the user's, sent once as an `(OOC: ...)` note in the last user turn (`requestTurns`). The wish is kept with the version it produced (`message.refines`, parallel to `variants`, the `refines` column; `refine` of `NewMessageExtra` and `addVariant`), never sent again, and shown small and grey above the reply by `RefineNote` in `MessageRow.tsx`: shimmering (`ShimmerText` with `wrap`) above the draft from the moment it is asked for (`refine` of `useChat`, of `RoomDraft` in a scene, carried on the draft `RowMessage`), then a tap offers what the user's own message has: Copy, Reply again (`refineAgain`: a new version with the same wish), Edit (`editRefine`: the refine prompt filled with it, a new version with what it becomes) and Delete (`dropRefine`, `removeRefine` of `useConversation`, `dropRefine` in `src/db/messages.ts`), which forgets the wish and keeps the reply. "Continue" sends a note of its own (`CONTINUE_NOTE`), which is not kept.

Private, the first item of the menu under the name in the header of a chat or a scene (`menu` in `ChatChrome` of `chat/[id].tsx`, there while the switch in Settings is on or the thread is open), opens it: a question to the model beside the story, like `/btw`. `useAside` keeps the thread in memory, `buildAsideRequest` (`src/lib/chat/aside.ts`) sends the scene brief and a text transcript of the latest lines (text, not assistant/user turns, so the model does not carry on in character), with the character's own `maxTokens`, `reasoningBudget` and thinking mode (in a room the largest limits of the cast), and `AsidePanel` shows it in the composer's `accessory` slot, so it rides the keyboard with the field. The jump-to-newest arrow is not in that slot: `ComposerFloat` draws it outside the swap, above the field and the slot, following the `top` shared value that `Composer` reports, so it stays when Private opens. Opening and closing swaps the whole field through `ComposerSwap` (`Composer.tsx`): the old one sinks, the new one springs up, and the chat's draft is kept in `initialText`/`onTextChange`. Nothing of it is saved or reaches the characters; closing the eye throws it away. The button is toggled by `src/db/prefs/privateChat.ts`.

After every finished reply `useSuggestion` (`src/hooks/chat/useSuggestion.ts`) asks `suggestReply` (`src/lib/chat/suggest.ts`, thinking off, the last six lines plus the scene brief from `AsideScene`, as many tokens as the "Suggestion length" slider under its switch in Settings, `src/db/prefs/suggestions.ts`) for the user's likely next message and hands it to `Composer` as `suggestion`. While the field is empty it replaces the placeholder, and a swipe to the right across the field types it in (a `Pan` in `Composer`). A swipe to the left dismisses it and `useSuggestion` asks for no more until the screen is left (its state lives with the chat). It streams in through `runReplyStream`, so the text appears as it is written; taking or dismissing it mid-stream aborts the request. Any new message, edit or open Private thread drops the suggestion. `src/db/prefs/suggestions.ts` holds the flag set in Settings > Chats (off by default). Rooms work the same way.

The streaming loop itself (reasoning, per-frame batching) is `runReplyStream` in `src/lib/chat/replyStream.ts`, shared with rooms.

The attach menu opens from the composer's plus button. On iOS it is the system form sheet (`src/app/attach/`, set in the root layout: detents 0.55 and full, grabber, solid background rather than the glass of a partial sheet) with a stack of its own, so the persona picker is pushed inside the sheet with the system bar, its glass back button and a + bar item; the main screen has a close item and a Photos item. The composer leaves an `AttachSession` (`setAttachSession`) and pushes `/attach`; a choice that must wait for the sheet to be gone (a picker, a screen pushed) is set with `setAttachAfter` and run by `finishAttachSession` on the sheet's closing `transitionEnd` (with a fallback after the layout unmounts), otherwise the field takes the keyboard back if it had it. Elsewhere it is `AttachSheet`, a `BottomSheet` with a solid background (`noGlass`) but Liquid Glass close and back buttons (`glassButtons`; the sheet then skips `overflow: hidden`, which would hide the glass; the glass buttons swap by scale alone, one mounted at a time, since glass does not render under a parent with opacity), where the persona picker slides in over the main screen and keeps its measured height (`minHeight`, the list too, so a drag below a short list scrolls it). The menu offers a camera tile, a horizontal scroll row of recent picture thumbnails with multi-selection checkmarks, file picking, the persona row, and a per-chat thinking toggle. With the row switched off in Settings, or with no picture sent yet, there is no row and no CTA, and the camera is a row of the card above files (the note about Settings shows only when it is switched off); the row comes with the first picture sent. The CTA button sits at the bottom: in its idle state it is neutral gray (`colors.surfaceRaised`) and disabled; once photos are selected, it smoothly transitions to the accent color (`colors.accent`) with white text via Reanimated opacity layers without UI-thread color crashes, showing the selected count and confirming attachment. Over the chat's background the bar under the button is a `BlurView` over it, not the sheet's color. Choosing a persona (`choosePersona`, which also updates the session) goes back to the main screen of the menu instead of closing it, so its persona row shows the new one. Persona rows separate row selection taps from the trailing ellipsis (`NativeMenu`) action button (edit/delete) so opening the menu does not trigger persona selection. In `GroupedList.tsx`, switches use a dedicated `switchRow` with symmetric vertical padding to stay centered against system `UISwitch` geometry.

## Rooms

A room is a cast of characters (`room_members`) and settings; its chats are scenes (`chats.room_id`, with `character_id` NULL). `chat/[id].tsx` shows a scene like a character's chat, on the same two threads and drawer, with `src/components/cast/RoomController.tsx` driven by `useRoom`. Its header is a chat's: the room's name and the scene's title in the pill under which the menu opens, and the cast as one round picture (`CastMosaic`) at the right end where a chat has the photo. Wherever a chat shows its character's photo, a scene shows its cast that way: `listRoomCasts` in `src/db/chats.ts` gives the `cast` of `LastChat` (the continue button) and `SearchChat` (search, the sidebar), null for a one-on-one chat.

1. The user picks addressees or the narrator in the cast sheet (opened from the button in `CastBar`: the system sheet `/cast` on iOS, `CastSheet` elsewhere, the same rows, `CastSheetContent`; with SwiftUI `/cast` is `NativeCastList`, the system's own list with the app's rows in it (`MemberContent`), the list's own swipe actions for walking in and out, its context menu for a long press (`menuItemViews` of `NativeMenu.tsx`, as a `DraggableCard` inside the row never got the press), the same menu from an ellipsis at the row's end and its switch for the whisper, a tap on someone out of the scene bringing them in and writing to them) and may switch on a whisper there. A swipe to the left on a member in the sheet walks them out of the scene or back in; a long press brings the system menu over the row on iOS (`DraggableCard` with `draggable={false}`), an action sheet elsewhere, with the same items (`memberItems` of `RoomController`). The message is saved with `addressees`, `audience`, `overheard` (rolled once from each member's perception) and `absent` (members out of the scene).
2. `planTurn` (`floor.ts`) scores the members and builds a queue for the room's floor mode: `addressee`, `reactions` or `open`. When the scores are too close it returns an `ambiguous` question, and `askDirector` asks the model with one short request (if the room allows it).
3. `useRoom.runQueue` generates the queued lines one by one. `buildRoomRequest` gives each speaker their own view: their lines as `assistant`, everyone else as `user` with a name in front, and nothing they could not hear (`hearing` in `audience.ts`). In open floor a line that calls another character by name queues their answer (`followUps`).
4. "Continue" and "Let them talk" use `nextSpeaker`; a nudge from the cast bar uses `turnFor`.

Each member has a secret, told to them alone (`secret` of `room_members`, in `buildRoomRequest` only for that speaker, so the others learn it only from what is said), and their feelings about the others (`bonds`), shared by every scene of the room. With the director on, `useRoom` keeps the room going by itself: every `CHRONICLE_EVERY` lines `askChronicle` notes, without holding the scene up, where it stands (`chats.scene_state`, "Right now:" in every speaker's prompt, and the pin shown in the status's place while nobody talks, `SceneState` in `RoomController`) and rewrites the feelings of whoever's changed; and with `plot` of the room above zero, after a turn that has run `EVENT_GAP` lines past the last event, the narrator may bring one in (`askEvent`, its strength by `plot`), which goes in as narration, may walk someone in or out, and gets a reaction.

The editor's "Set up with AI" fills all of this in from a few words: the scene with its relationships, the opening, the floor, and each member's talkativeness, perception and triggers (`roomGen.ts`, see Find it fast).

Members can be muted (listen only) or out of the scene (hear nothing); entering and leaving is recorded as a narrator line (`useRoom.setPresent`). With the director on, the characters move by themselves too: after every line `movementCue` (`floor.ts`) looks for words of going or coming, and only then `askMovement` (`director.ts`) asks who actually left or came in. In open floor whoever came in gets a turn to react.

## Data on disk

`src/lib/core/storage.ts` decides where the database (`SQLite/reverie.db`) and the `avatars`, `backgrounds` and `attachments` folders live: in Documents, which the Files app shows, or in the private `Library/Reverie` (a dot-folder in Documents under Expo Go). A `show-in-files` marker file in the private folder says which one.

- The private folder path must not contain a space: expo-sqlite parses the directory with `URL(string:)`, which on iOS 17+ turns a space into `%20` and opens a new empty database elsewhere. Versions 2.2 to 3.0 had exactly this bug with `Library/Application Support/Reverie`.
- `settle()` runs once on import, before the database opens. It moves the files to where the marker says and picks up what older versions left behind (`Application Support/Reverie`, `Application%20Support/Reverie`, Documents). If several databases turn up, the one the app was last showing is kept, and the others are moved to `Library/Reverie/earlier-databases/`, never deleted.
- The toggle works without a restart: `useShowInFiles` calls `moveStorage`, which copies the open database with `VACUUM INTO`, moves the images and flips the marker. Then `DatabaseProvider` opens the copy and hands it down in place of the old one, and screens reload through their `[db]` effects. The old database is closed after that re-render, and `discardInactiveDatabase` removes it.

## Folder sync

A folder the user picks, on either platform: in iCloud Drive or Google Drive, in any other storage the system picker offers, or a plain local one. Not the iCloud entitlement: that one needs a paid developer account, and the app is signed with a free Apple ID. `modules/reverie-cloud-folder` is a local Expo module (autolinked from `modules/`) with one JS interface and two native sides:

- iOS (`ios/ReverieCloudFolderModule.swift`): the document picker, a bookmark in `UserDefaults`, and every read and write under `NSFileCoordinator`, which is what makes iCloud download a placeholder and upload a new file.
- Android (`android/.../ReverieCloudFolderModule.kt`): `ACTION_OPEN_DOCUMENT_TREE`, a persisted permission on the tree uri (kept in `SharedPreferences`), and `DocumentFile` for the reads and writes. A file is written over in the `wt` mode instead of being deleted and made again, which some providers turn into a copy under a new name.

It is missing in Expo Go, and then the Settings block is hidden (`cloudSyncAvailable`). The switch was stored as `icloud_sync` before the sync stopped being iCloud only; the key was renamed to `folder_sync` without a migration, so a device that had it on shows it off once, and turning it on again picks up the folder that is still remembered.

- In the folder: `manifest.json` (the revision, written last), `reverie.db` (a `VACUUM INTO` snapshot with `app_settings` removed under `secure_delete`, so the API key never leaves the device) and `avatars/`, `backgrounds/`, `attachments/` by their unique names.
- A device remembers the revision it last matched (`sync_rev`) and whether anything changed since (`sync_dirty`). Only one side changed: it wins. Both: a sheet asks which one to keep, and if it is the folder's, the local database is first put aside in `earlier-databases` (`keepCopy` in `storage.ts`).
- A pull writes the rows straight into the open database from the attached copy (older copies are migrated first, newer ones refused), then `useReloadDatabase` hands the screens a new connection. The database in the folder is never opened in place.
- `CloudSyncProvider` syncs on start and on coming to the front, and pushes on going to the background. Quiet runs only log errors.
- Settings also has Push and Pull, one way each, like git: a push is refused when the folder has a revision this device has not seen (`behind`), a pull when this device has changes of its own (`conflict`), and both then ask before going ahead with `local` / `cloud`. Their errors are shown.
- Sync uses a connection of its own: `ATTACH` fails inside a transaction, and the app's connection may be in one.

### Liquid Glass

On iOS 26 the controls are Liquid Glass through `GlassSurface` in `Glass.tsx`; it takes a `fallbackStyle` for older iOS, where the same control is the plain surface with a hairline. `nativeUI.ts` says whether glass is available (`liquidGlass`).

- **Buttons:** `Button` (`variant="glass"` for the one call to action, `variant="solid"` for the same capsule filled without glass: the foot of onboarding and of the app icon picker), `PillButton` for secondary actions (label in the action's color, `colors.danger` for deleting; `filled` tints the glass with that color under a white label, for backup and delete buttons), `GlassButton` / `GlassGroup` for round icon buttons. `GlassButton` with `tint` fills with the accent; the save checkmark of `DrawnFormScreenHeader` is one (`prominent`).
- **Choices:** `Chip` (not interactive glass, whose press spring pulls it along with the sideways scroll of `ChipGroup`; the press scale is only for the non-glass fallback), tinted with the accent when chosen. It stays regular glass: made clear, it turned the accent-tinted `StarToggle` next to it blue in the dark scheme.
- **Switches:** the system `Switch` (also the whisper row of the cast sheet). `StarToggle`, a round 44 pt glass button with the brand star (clear with an outlined star when off, accent with a white star when on, the star swinging over with a spring), is kept in `motifs/` but no longer used.
- **Inputs:** `Field` and `PickerBox` are a rounded box (radius 14) with a hairline, as in the first releases, not glass. The forms (Settings, both editors, the prompt sheet) are grouped lists instead. The chat `Composer` is still clear glass, tinted with `accentSoft` while focused: a capsule for one line (the plus and the send button inside it; the plus opens an attach menu in a bottom sheet (`BottomSheet` with "Add to Chat" title, top row with Camera tile and recent image thumbnails with "Photos" action in the header, first card with "Add files" and a "Persona" row with smooth sub-screen slider navigation, and a second card with the per-chat thinking switch; when `recentAttachments` is enabled, recent pictures show as tiles alongside camera; a little narrower while the field is not focused), a rounded box for several, where the text takes the full width and the plus and the send button drop to a row under it (a hidden `Text` at the one-line width counts the lines, so widening cannot flip it back). A `TextCell` shows the first lines of a long text, and a tap opens it for editing in `/text-editor`, zooming out of the row (`Link.AppleZoom`).
- **Cards:** `ListCard` across characters, groups, rooms and chats is clear glass (`GlassSurface variant="clear"` with no fill under it; the old solid cards look was replaced with glass blocks). The glass is a sibling of the content, not inside it: a clipped glass loses its rim at the corners.
- **Pressing:** interactive glass springs under the finger by itself, so glass controls add no press scale of their own (the two fight and the control jumps); the scale stays only on the non-glass fallback.
- **Tint changes:** `tools/patches/expo-glass-effect+*.patch` (applied by `patch-package` on `postinstall`) makes a change of `tintColor` on a mounted glass view fade over 0.3 s instead of snapping: UIKit animates only a switch to a new effect object, so the patch builds a fresh `UIGlassEffect` and sets it in `UIView.animate`, after the mount pass. Re-create the patch when updating `expo-glass-effect`.
- **Text fields of the system's list:** `tools/patches/@expo+ui+*.patch` keeps `@expo/ui`'s `TextField` from putting back the selection it has just reported from the field: put in again, it reset a selection being made (the generator's result could not be copied) and, with Cyrillic text, could point past the end and crash in UIKit. Re-create the patch when updating `@expo/ui`.
- **Solid system sheets:** a `formSheet` below the full height is interactive Liquid Glass on iOS 26+, and the whole sheet squeezes and flares under any touch on it; `contentStyle` only paints over the glass. `tools/patches/react-native-screens+*.patch` sets the sheet's `backgroundEffect` (iOS 26.1) to a `UIColorEffect` in the color the screen paints (the first opaque full-size view under it, else the system background), which replaces the glass, for every form sheet. Re-create the patch when updating `react-native-screens` (upstream issue #4605).
- **Corners:** glass draws continuous (squircle) corners, so anything that sits on it or clips next to it uses `borderCurve: 'continuous'`.
- **Icons on the accent:** `SFIcon` with `onAccent`. SwiftUI draws a symbol dark in the light scheme even with an explicit white color, so the hosted view gets the dark scheme instead.
- **SF Symbols everywhere:** `Icon` (`src/components/visuals/Icon.tsx`) takes the Ionicons names and on iOS with `@expo/ui` draws the matching SF Symbol (`SF`: an outline and a filled form, by the `-outline` suffix), falling back to Ionicons for a name it lacks; a white one is hosted in the dark scheme for the reason above.

## Alternate app icons

Four icons besides the standard one (which follows the light and dark look from `app.json`), chosen in Settings > App icon: Sunrise, Paper, Violet and sun, Metal. Their internal names (`CoralSunrise`, `PaperLight`, ...) are older than the drawings and stay, so a chosen icon survives an update.

- Source: `assets/brand/alt/icon-NN-name.svg`, exported from Penpot (page "Logos Design", group "Icons") with `penpot.generateMarkup` per layer. Each is an SVG in the page's coordinates (the `viewBox` starts at the board's corner) whose parts are marked with comments: `<!--bg-->`, `<!--glyph-->` (the letter, the spark and the Sunrise flash) and `<!--top-->` (what lies over the glyph, such as Paper's creases).
- `tools/build-icons.mjs` renders each to `assets/images/alt/`: the 1024 icon (iOS), a 660 preview (the picker shows it up to 220 pt, at 3x) and a `-foreground` layer (Android). For Android the background and the top layer are stretched past the edges and the glyph shrunk into the middle two thirds, as a launcher's mask cuts the rest (`GLYPH` says where the glyph sits).
- `expo-alternate-app-icons` (a plugin entry in `app.json`: name, iOS image, Android foreground and background color) puts them into the native projects on `expo prebuild`: `CFBundleAlternateIcons` on iOS, one `activity-alias` per icon on Android. The names there, in `src/lib/settings/appIcons.ts` and in the `appIcon.*` strings must match.
- `appIcons.ts` reaches the native module with `requireOptionalNativeModule`, since the package's own entry throws on import in Expo Go, which has no such module; then the Settings row is hidden (`alternateIconsAvailable`), except in a development build, where the picker shows and the choice is only kept in memory, so its look can be checked in Expo Go.
- Light and dark: Paper is drawn in both looks of the Home Screen (`icon-04-paper-dark.svg` beside it) and also comes tinted, since iOS 18 takes the three together. `VARIANTS` in `build-icons.mjs` names the other look's file and recolors the glyph for the tinted one (on black, without shadows); the plugin entry takes `{ light, dark, tinted }`, and the picker shows the preview of the current look (`previewFor`). Android launchers have no dark icons, so there it stays one, and the picker shows that one (`android` in `APP_ICONS`: the light Paper, the dark standard icon) and no "Light and dark" under it.
- A new icon: add the SVG (with the three marked parts), a plugin entry, a line in `APP_ICONS` (with the `glow` color the picker lights the page with behind it) and a name in both locales.

## Conventions

- Screens stay thin: data access in `src/db`, logic in `src/lib` or hooks.
- Strings always go through `t('key')`; add the key to both locale files.
- New setting flag: new `src/db/<name>.ts` with `defineFlag(key, default)`, a row in `(tabs)/settings.tsx`, strings in both locales. To make it findable, wrap the row in `block('<section>', …)`, add the id to `SettingsSection` and an entry to the settings list in `(tabs)/search/index.tsx`.
- New column: append a migration, extend the `*_COLUMNS` constant and the type, and bump `BACKUP_VERSION` in `backup.ts` if the backup should carry it (older backups must still import).
- Check types with `npm run typecheck`.

## Android

The same code base, with the iOS-only parts replaced or left out.

- `nativeUI.ts` loads `@expo/ui` (SwiftUI) and `expo-glass-effect` only on iOS, so `swiftUI` and `liquidGlass` are null on Android and every component takes its fallback path. `ExpoUI` registers a module on Android too, which is why the platform is checked and not only the module. Every SwiftUI `Host` takes `ignoreSafeArea="all"`: without it a host mounted over the home indicator or the keyboard takes their inset and draws its content shifted inside its frame until it is laid out again.
- `ActionSheetIOS` and `Alert.prompt` do not exist on Android. `showSheet` and `promptText` in `src/lib/ui/dialogs.tsx` hand the request to `src/lib/ui/dialogStore.ts`, and `DialogHost` (mounted in `src/app/_layout.tsx`) draws it in a `Modal`. `NativeMenu` falls back to `showSheet`, so its menus are a bottom sheet there. A `MenuItem` with `children` is a submenu: a nested SwiftUI `Menu` on iOS, a second sheet opened by the first elsewhere.
- Tabs: `NativeTabs` has Material icons (`md`) next to the SF Symbols and, unlike iOS, insets the content by the tab bar itself.
- Storage: no `Library` folder and no Files app. The data sits in `files/Reverie` and the "show in Files" toggle is hidden (`settings.tsx`, search entries).
- No blur on Android (it costs a copy of the screen per frame): `BlurBar` is a nearly opaque tint, the app lock shield a solid color. The chat `Composer` is not in a bar there: its solid field floats over the messages with the `EdgeFade` under it, as with Liquid Glass. The photo, and the name with the chat title, in the chat header sit in a solid circle and pill (`glass.solid`), like the glass ones on iOS.
- `reverie-save-as`, `reverie-fonts`, `reverie-drag` and `reverie-splash` are Swift only (on Android the cards keep the plain menu and no drag), while `reverie-cloud-folder` has a Kotlin side too, so folder sync works on Android. Missing there, so: saving a backup uses the folder picker, and the font menu lists the Android system families (`serif`, `monospace`, ...). The default chat font is `serif` instead of Georgia.
- The lock row says "screen lock" (`settings.requireBiometrics`) instead of Face ID.
- The search screen has a solid header on Android: `contentInsetAdjustmentBehavior` is iOS only.
- Icons: `tools/build-icons.mjs` also renders the adaptive and monochrome Android icons.
